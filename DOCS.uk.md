## Налаштування Telegram

Створіть бота через [@BotFather](https://t.me/BotFather), додайте його до потрібного чату та зберігайте токен приватно. Окремий бот для цього застосунку допоможе уникнути конфліктів між збирачами оновлень.

| Призначення | Налаштування |
| --- | --- |
| Особиста розмова | Відкрийте бота й натисніть **Розпочати**, щоб він міг вам писати. |
| Група/супергрупа | Додайте бота, дозвольте повідомлення. Для закріпленого статусу надайте право закріплення. |
| Канал | Додайте бота адміністратором із правами публікації та редагування своїх повідомлень. |

### Найпростіше: повідомлення лише собі

Створіть бота, натисніть **Розпочати**, знайдіть ID особистого чату за інструкцією нижче й задайте його в `telegram_chat_id`. Особистий ID додатний, наприклад `"123456789"`; для груп і каналів збережіть мінус. Не підставляйте свій `@username` замість числового ID.

Налаштуйте адресу в HA та увімкніть потрібні повідомлення. `feedback_enabled` для звичайного надсилання не потрібен. Натискання Start дозволяє боту писати вам, але не реєструє адресу чи підписку автоматично: це бот сповіщень із налаштуванням у HA, а не майстер налаштування командами Telegram.

Якщо не потрібне закріплення, вимкніть `status_message.pin` або весь `status_message.enabled`. Значення `delivery_mode: pinned_edit` разом із `pin: false` продовжує редагувати одне звичайне повідомлення. У групі це також дає змогу працювати без права закріплення. [Права закріплення Telegram](https://core.telegram.org/bots/api#pinchatmessage).

Для кожної адреси задається одне призначення; автоматичної підписки довільних користувачів чи налаштування окремих тем форуму наразі немає. Якщо група перетворилася на супергрупу та її ID змінився, оновіть ID в параметрах і перезапустіть застосунок.

### Як знайти ID чату

Якщо цей чат уже використовується в довіреній конфігурації HA, скопіюйте числовий ID звідти. Інакше отримайте його безпосередньо від Telegram через власного бота:

1. Зупиніть усі застосунки, які отримують оновлення цього бота. Зробіть це **до** ввімкнення збору зворотного зв’язку.
2. Надішліть нове повідомлення: `/start` в особистій розмові, `/start@YourBotUsername` у групі або звичайний допис адміністратора в каналі.
3. Збережіть код нижче як `telegram_chat_id.py` на комп’ютері з Python 3 і запустіть `python3 telegram_chat_id.py`. Він запитає токен без відображення введення та покаже ID й назви чатів. Повідомлень не надсилає, оновлень не підтверджує.
4. Скопіюйте ID потрібного чату разом зі знаком мінус до `telegram_chat_id`. Закрийте скрипт перед запуском застосунку.

```python
import getpass
import json
import urllib.error
import urllib.request

bot_token = getpass.getpass("Токен бота: ")
request = urllib.request.Request(
    "https://api.telegram.org/bot" + bot_token + "/getUpdates",
    data=b"timeout=0",
)
try:
    with urllib.request.urlopen(request, timeout=20) as response:
        payload = json.load(response)
except urllib.error.URLError:
    raise SystemExit("Помилка запиту. Перевірте токен, мережу й інші збирачі.") from None
seen = set()
for update in payload.get("result", []):
    message = update.get("message") or update.get("channel_post") or {}
    chat = message.get("chat", {})
    if "id" in chat and chat["id"] not in seen:
        seen.add(chat["id"])
        print(chat["id"], chat.get("title") or chat.get("username") or chat["type"])
if not seen:
    print("Чат не знайдено. Надішліть нове повідомлення та повторіть спробу.")
```

Налаштований webhook конфліктує з `getUpdates`; не видаляйте webhook іншого сервісу лише заради тесту. Використайте окремого бота. [API оновлень Telegram](https://core.telegram.org/bots/api#getupdates) і [правила приватності ботів](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get) пояснюють, які нові повідомлення він отримує. Бот не є універсальним засобом читання історії чатів.

<a id="configuration"></a>
## Де зберігаються параметри

Є два рівні конфігурації:

| Місце | Параметри |
| --- | --- |
| Вкладка **Конфігурація** застосунку в HA | `telegram_bot_token`, `telegram_chat_id`, додаткові `test_chat_id`, `feedback_enabled` (типово `false`). Після зміни перезапустіть застосунок. |
| Вебредактор застосунку | Адреси, правила живлення/напруги, сповіщення та шаблони. Зміни адрес і робочих параметрів застосовуйте через **Зберегти й перезапустити**. |

Редактор записує робочі параметри до `dtek_telegram_bot.yaml` у каталозі конфігурації HA. Усередині цього застосунку шлях — `/homeassistant/dtek_telegram_bot.yaml`; у файловому редакторі HA той самий файл може бути видимим як `/config/dtek_telegram_bot.yaml`. `/data/config.yaml` — запасний шлях; наявна запасна конфігурація копіюється, коли основний шлях уперше стає доступним. Не підтримуйте різні конфігурації у двох файлах.

`ha_token` — необов’язковий резервний токен авторизації HA. За звичайного запуску через Supervisor залиште його порожнім. Повний експорт конфігурації може містити цей токен і приватні адреси: перевірте його перед публікацією.

### Безпечне редагування

Фонове оновлення показує живі дані та не замінює поля, які ви редагуєте. **Перевірити** перевіряє поточну чернетку й показує знімок її результату, але не зберігає її. **Зберегти конфіг** записує налаштування; **Зберегти і перезапустити** також застосовує їх до запущеного застосунку. Якщо продовжити введення під час збереження, пізніші зміни залишаться незбереженими.

Чернетки конфігурації та окремих шаблонів переживають перезавантаження сторінки в тій самій вкладці, якщо доступне сесійне сховище браузера. Закриття вкладки може їх видалити; важливу чернетку конфігурації спочатку експортуйте. Перемикання шаблонів чи адрес не стирає їхні чернетки. Прев’ю використовує поточний текст без збереження.

Якщо інша вкладка або редагування файлу змінить збережену версію, застосунок повідомить про конфлікт замість перезапису. Експортуйте чернетку конфігурації (або скопіюйте текст шаблону), натисніть **Завантажити збережене** й узгодьте зміни. Ця дія відкидає поточну чернетку після підтвердження.

### Поля адреси

| Поле | Значення |
| --- | --- |
| `entity_prefix` | Спільна частина ID сутностей адреси. Використовуйте автоматичне виявлення: це не обов’язково назва вулиці. |
| `display_name` | Зрозуміла назва в повідомленнях; порожня дозволяє визначити її через HA. |
| `telegram_chat_id` | Окремий чат адреси; порожній використовує основний. Тестове спрямування має пріоритет над обома. |
| `selected_group` | Порожнє поле відстежує всі групи адреси. Обирайте лише відому вам групу. |

Наприклад, для `sensor.dtek_krem_0123456789abcdef_outage_status` префікс — `dtek_krem_0123456789abcdef`. Якщо збережена обрана група зникає з адреси, обробка графіка очікує коректного вибору, а не вгадує заміну.

Для операторів із прихованими ID зазвичай залишайте `selected_group` порожнім і використовуйте відображувані варіанти. Звернення до регіональних сайтів і вибір оператора належать до [DTEK Monitor](https://github.com/groove-max/ha-dtek-monitor/blob/main/README.uk.md).

## Налаштування фактичного стану живлення

Спочатку скористайтеся [таблицею режимів](README.uk.md#power-detection). ID нижче — приклади: замініть їх через виявлення адрес і сторінки пристроїв HA.

### Один датчик: `voltage_only`

Датчик має вимірювати **напругу на вході мережі у вольтах**, працювати під час відключення та передавати реальні значення, зокрема нуль. Його мережа/шлюз і HA також потребують резервного живлення. Налаштуйте періодичне передавання навіть незмінних значень. Датчик частоти не можна вказувати в `voltage.entities`.

Повний приклад робочого YAML для однієї адреси. `voltage.enabled: false` вимикає окремі сповіщення про якість напруги, а не використання вимірювань для визначення живлення:

```yaml
addresses:
  - entity_prefix: dtek_krem_0123456789abcdef
    display_name: Приклад будинку
    power:
      enabled: true
      mode: voltage_only
      loss_delay: 10
      restore_delay: 30
      telemetry_notifications: false
    voltage:
      enabled: false
      entities:
        - entity: sensor.inverter_ac_input_voltage
          label: L1
      present_above: 50
      max_age_seconds: 150
```

`loss_entity` і `loss_mqtt_topic` залишаються порожніми. `confirm_timeout` у цьому режимі не застосовується. Якщо єдиний датчик вимикається разом із мережею, він придатний для вимірювання наявності напруги, але його зникнення не підтверджує відключення.

### Два датчики: `loss_plus_voltage`

Використайте резервований датчик втрати мережі **на тій самій лінії** разом із лічильником напруги, наприклад ATORCH. Незалежне джерело має явно повідомляти про відсутність мережі: наприклад, частота на AC-вході інвертора нижча за 1 Гц. Недоступність цього датчика не є сигналом втрати мережі.

Замініть секції `power` і `voltage` всередині адреси цим прикладом:

```yaml
power:
  enabled: true
  mode: loss_plus_voltage
  loss_entity: sensor.inverter_ac_grid_frequency
  loss_state: "<1"
  loss_delay: 10
  confirm_timeout: 15
  restore_delay: 30
  telemetry_notifications: false
voltage:
  enabled: false
  entities:
    - entity: sensor.atorch_voltage
      label: L1
  present_above: 50
  max_age_seconds: 150
```

| Показання | Результат |
| --- | --- |
| Свіжий сигнал втрати мережі від інвертора + недоступний ATORCH або старе завмерле значення | Підтверджене відключення після затримок підтвердження й втрати. Порядок подій неважливий. |
| Сигнал втрати мережі + нова додатна напруга після нього | Суперечність: сигнал не перекриває свіжої напруги. |
| ATORCH недоступний, інвертор показує наявність мережі | Невідомий локальний стан, без хибного відключення. |
| Обидва джерела застарілі/недоступні | Невідомо, а не підтверджена втрата живлення. |
| Інвертор показує повернення мережі, ATORCH ще недоступний | Очікування свіжої напруги перед повідомленням про відновлення. |
| Свіжа напруга повернулася та залишається достовірною протягом затримки | Повідомлення про відновлення, якщо раніше відключення було підтверджене. |

Повторні повідомлення про недоступність не перезапускають таймери та не перетворюють підтверджене відключення на тимчасову втрату даних, доки незалежний сигнал відсутності мережі залишається свіжим.

### Затримки та актуальність

Значення у прикладах — початкові орієнтири для джерела, яке звітує приблизно раз на хвилину, **а не універсальні рекомендації для пристроїв чи типові значення**.

| Параметр | Типово | Призначення |
| --- | --- | --- |
| `power.loss_delay` | 30 с | Стійка відсутність перед повідомленням про втрату живлення. |
| `power.confirm_timeout` | 15 с | Час підтвердження у режимі двох сигналів перед відхиленням старої напруги. |
| `power.restore_delay` | 10 с | Стійка достовірна наявність перед відновленням. |
| `voltage.max_age_seconds` | 600 с | Максимальний вік показання; доберіть за реальним інтервалом звітування. |
| `voltage.present_above` | 50 В | Напруга від цього програмного порога вважається наявною. |
| `power.telemetry_notifications` | `false` | Окремі сповіщення про втрату/повернення даних. Статус оновлюється й без них. |
| `power.telemetry_loss_delay` | 20 с | Затримка необов’язкового сповіщення про втрату даних. |

Свіжа низька/нульова напруга може підтвердити відсутність. Відсутні, некоректні, від’ємні, нескінченні, відновлені зі сховища чи застарілі значення самі по собі цього не підтверджують. Перевірка кожні 5 секунд виявляє мовчазне старіння даних. Незмінне, але щойно передане значення придатне; повторні показання не перезапускають затримку. Невідомі або суперечливі дані переривають очікуваний перехід.

У прикладі з двома датчиками враховуйте близько 15 + 10 секунд після отримання незалежного сигналу втрати та час обробки/перевірки. Щоб оцінити затримку від фізичного відключення, додайте інтервал звітування пристрою. Максимальний вік даних — не затримка підтвердження відключення.

`last_reported` HA (або запасний `last_updated`) фіксує звітування в HA, а не гарантовано нове вимірювання на пристрої. Хмарна інтеграція може повторно публікувати старі дані. Старий параметр `unavailable_as_missing` збережений для сумісності, але більше не перетворює відсутність даних на відключення.

### Незалежне джерело MQTT

Для MQTT-датчика втрати мережі можна вказати точний топік стану в `power.loss_mqtt_topic`. Застосунок пасивно підписується через HA, ігнорує повторне retained-повідомлення та вимагає свіжого повідомлення, яке збігається зі станом сутності. Маски топіків не приймаються. З’єднання HA має дозволяти `mqtt/subscribe` — потрібен адміністраторський доступ. Облікові дані MQTT-брокера цьому застосунку не потрібні.

Використовуйте активний топік пристрою, а не старий із залишеним retained-значенням. Якщо MQTT-сенсору HA потрібен числовий шаблон, `{{ value | float(none) }}` обробляє числовий текст/байти, не перетворюючи помилковий вміст на нуль. Це налаштування MQTT-сенсора HA, а не шаблону Telegram. Дивіться [поведінку MQTT-сенсорів HA](https://www.home-assistant.io/integrations/sensor.mqtt/).

### Кілька фаз

Додайте сутності напруги з підписами `L1`, `L2`, `L3`. `on` означає наявність усіх налаштованих фаз; `off` потребує доказів відсутності всіх. `partial` — частина живлення є, а інші фази відсутні або невідомі; статус розрізняє ці випадки. Невизначеність не створює сповіщення про втрату фази. Незалежний сигнал має описувати саме контрольовану лінію/схему живлення.

Раніше підтверджене відключення зберігається в історії після втрати даних, тому достовірне повернення напруги все ще може спричинити повідомлення про відновлення. Якщо прогалини заважають обчисленню тривалості, вона позначається як невідома.

<a id="notifications"></a>
## Які сповіщення ввімкнути

Кожна функція має `enabled`. `silent` вимикає звук сповіщення Telegram, **а не саме повідомлення**.

| Секція | Призначення / основні параметри |
| --- | --- |
| `schedule_change` | Зміни опублікованого графіка; порожній графік оголошується лише за достатнього покриття публікації. |
| `group_change` | Зміна груп адреси та їхній графік; без дубля повідомлення про той самий графік. |
| `emergency` | Початок/завершення, причина та орієнтовний час відновлення за даними оператора. |
| `upcoming_outage` | `minutes` до початку (типово 10); `power_filter`: `always`, `only_when_available` (типово), `only_when_missing`. |
| `power` | Втрата/відновлення за обраним режимом; додаткові `phase_notifications`. |
| `voltage` | Окремі сповіщення про напругу: типово `low: 195`, `high: 245`, `hysteresis: 5`, `delay: 15`. |
| `status_message` | `pinned_edit` (типово) або `send_new`; `pin`, `silent`, `update_interval` (300 с), `min_update_interval` (10 с). |

Для повернення напруги в норму застосовується гістерезис: після виходу за межу значення має повернутися всередину нормального діапазону на заданий запас. Для спільного чату почніть із закріпленого статусу й потрібних мешканцям подій. У режимі `dtek_only` одночасно ввімкнені повідомлення про відключення ДТЕК та живлення можуть двічі описати ту саму подію оператора — оберіть потрібні категорії.

Графік і локальні вимірювання залишаються окремими джерелами. Під час збою ДТЕК контроль фактичного живлення може продовжуватися; збережені графіки не запускають автоматичних повідомлень про графік, групи чи наближення відключення.

<a id="templates"></a>
## Як змінити текст повідомлень

Відкрийте **Шаблони**, оберіть шаблон, перегляньте результат, відредагуйте й збережіть перевизначення. Скидання видаляє власний варіант і повертає стандартний. Тестове надсилання публікує справжнє повідомлення в налаштованому чаті.

Використовується Jinja. Доступні поля показані в редакторі й залежать від повідомлення. `group`, `groups`, `selected_group`, `old_group`, `new_group` уже враховують приховані підписи; `groups_public` показує, чи існують публічні номери груп.

Розміщуйте заголовок, інтервал і пояснення на окремих рядках. Обрізання пробілів Jinja прибирає перенос після блочного тегу, наприклад `{% endif %}`: перевіряйте **готовий текст** для всіх гілок шаблону. Явний `{{ '\n' }}` дозволяє зберегти потрібний перенос.

Перевизначення зберігаються в `/data/templates/*.j2` і переживають оновлення. Тому нова версія застосунку не виправить старий власний шаблон автоматично. `export_default_templates: true` копіює стандартні файли лише за їх відсутності; залиште вимкненим, якщо вони вам не потрібні.

<a id="testing"></a>
## Тестування без повідомлень в основний чат

1. Виберіть тестовий чат: натисніть **Розпочати** в особистій розмові або додайте бота до тестової групи/каналу з потрібними правами.
2. Задайте `test_chat_id` у параметрах застосунку та перезапустіть його.
3. Усі надсилання, редагування, закріплення й відкріплення тепер спрямовані туди, включно з окремими чатами адрес і тестами інтерфейсу. Змінювати/закріплювати можна лише повідомлення, відомі тестовому журналу.
4. За потреби ввімкніть `feedback_enabled`, щоб збирати нові доступні боту дописи цього тестового чату. На один токен має працювати один збирач; налаштований webhook заважає його запуску.
5. Під час тесту зупиніть робочий екземпляр із тим самим токеном. Тестовий стан ізольований у `/data/test-<identity>/`.

Вхідний зворотний зв’язок залежить від прав і приватності Telegram. У каналі без прив’язаної групи обговорень використовуйте дописи адміністратора, а не очікуйте відповідей користувачів. Збирач не імпортує довільну стару історію чату.

Локальний SQLite-журнал містить вихідні тексти, результати API та контекст адрес/груп; зворотний зв’язок додає вхідні повідомлення. Зберігається до 10 000 записів подій. Це приватні дані. Супроводжувач може читати `telegram.sqlite` через SSH у режимі SQLite лише для читання. Журнал підтверджує результат доставки, а не прочитання людьми.

Явні тимчасові помилки можуть спричинити обмежені повтори після перевірки актуальності. Неоднозначні мережеві результати записуються як невизначені, без сліпого повторного надсилання. Гарантії доставки «рівно один раз» тут немає.

<a id="updates"></a>
## Резервні копії, оновлення та перенесення

- Зберігайте резервні копії даних застосунку та конфігурації HA, включно з `dtek_telegram_bot.yaml` і власними шаблонами.
- Прочитайте [історію змін](CHANGELOG.md), оновіть застосунок і перевірте активні параметри та чат.
- Для перенесення використайте експорт/імпорт адрес або чернетки конфігурації. Це не створює сутностей HA й не переносить параметри Supervisor: токен/чат задайте окремо, ID сутностей узгодьте вручну.
- Перед виходом із тестового режиму зупиніть тестовий екземпляр, очистьте `test_chat_id`, перевірте основний чат і перезапустіть. Робочий режим відновлює власний збережений стан; не копіюйте тестові ID повідомлень або чергу сповіщень у нього.

Облікові дані Telegram зберігаються в параметрах Supervisor, резервний токен HA може бути в робочому YAML. Включайте їх лише до приватних копій. Якщо токен став публічним, замініть його через сервіс, який його видав.

Якщо проблему не розв’язано, скористайтеся [таблицею діагностики](README.uk.md#troubleshooting), потім створіть issue з версіями, режимом, інтервалом звітування та потрібними журналами без приватних даних. Для розробників є [посібник учасника](CONTRIBUTING.uk.md).
