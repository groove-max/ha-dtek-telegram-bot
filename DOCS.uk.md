<a id="dtek-monitor"></a>
## Підключення DTEK Monitor

Будинковий режим підтримує публічні сутності DTEK Monitor 1.7.0, 2.0.0b1 та 2.0.0-rc4. Потрібен HA 2026.3.0+. Адреси підтримуються в Одеській, Київській, Дніпропетровській областях і місті Києві.

| Потрібний сценарій | Налаштування |
| --- | --- |
| Канал/група будинку або повідомлення лише собі за адресою | Будинковий режим; оберіть адресу через виявлення. |
| Будинок, прив’язаний до рахунку в «Мій ДТЕК» | Перевірте прив’язку в налаштуваннях кабінету, потім оберіть цей будинок у боті. |
| Особисті групи кабінету, покази й нагадування | Особистий профіль; потрібні бот 0.5.0-rc4 і Monitor 2.0.0-rc4. [Повна інструкція](docs/PERSONAL.uk.md). |

Для спільного чату залиште `selected_group` порожнім: будинковий режим збереже всі групи адреси. У цьому режимі можна обрати підтверджену групу вручну; вибір у панелі «Мій ДТЕК» його не змінює. Особистий режим натомість бере групи лише з API кабінету, без ручної підміни або переходу до груп будинку.

Виявлення будинків використовує спільний префікс ID їхніх сутностей. Перейменування окремих ID може порушити сповіщення; назву для повідомлень змінюйте в редакторі. Особистий режим має окремий список рахунків; пароль ДТЕК у боті не зберігається.

<a id="monitor-upgrade"></a>
### Оновлення інтеграції DTEK Monitor

Ця версія доступна у звичайному каналі HACS. Налаштування на 1.7.0, які вже працюють, можуть продовжувати використовувати бота. Проте 1.7.0 має [відому проблему першого налаштування](https://github.com/groove-max/ha-dtek-monitor/issues/5): коли графік не опубліковано, завантаження може постійно повторюватися без створення сутностей адреси. **У 2.0.0b1 цей випадок виправлено**: адреса завантажується незалежно від доступності графіка.

1. Створіть повну резервну копію HA з файлами інтеграції, `.storage`, даними застосунку, `dtek_telegram_bot.yaml` і власними шаблонами.
2. У HACS виберіть [останній сумісний випуск DTEK Monitor](https://github.com/groove-max/ha-dtek-monitor/releases/latest) (**2.0.0-rc4 або новіший**) та перезапустіть HA. Перемикач попередніх версій не потрібен; скористайтеся [інструкцією встановлення](https://github.com/groove-max/ha-dtek-monitor/blob/main/docs/UPGRADING.uk.md).
3. Збережіть наявний запис інтеграції та адреси бота. ID сутностей, чати, прив’язки датчиків і вибір груп мають залишитися незмінними.
4. Перевірте, що запис інтеграції завантажився, бот відновив з’єднання з HA, а локальні датчики передають свіжі значення. Сама відсутність опублікованого графіка не означає збій оновлення.
5. Якщо змінюєте параметри бота, використовуйте **Застосувати**. Для необов’язкової перевірки доставки спочатку виберіть [тестовий чат](#testing).

Версія 2 змінює формат конфігурації інтеграції. **Для повернення до 1.7.0 потрібно відновити резервну копію до оновлення**, включно з конфігурацією та старими файлами інтеграції; лише перевстановлення старого коду недостатньо. Дивіться [інструкцію відкату інтеграції](https://github.com/groove-max/ha-dtek-monitor/blob/main/docs/UPGRADING.uk.md).

<a id="schedule-availability"></a>
### Як розуміти відсутній графік

У Monitor 2.0 окремо перевіряйте сутності будинку **З’єднання з ДТЕК** та **Доступність графіка**. З’єднання може працювати, хоча добовий графік ще не опубліковано. Доступність описує дані на сьогодні за київським часом для відповідних груп:

| Стан | Значення |
| --- | --- |
| `current` | Повний добовий графік перевірено; він містить планові відключення. |
| `empty` | Повні добові дані підтверджують відсутність планових відключень для цієї дати та груп. Аварійні відключення все одно можливі. |
| `partial` | Перевірене добове покриття є лише для частини груп або дня. |
| `forecast` | Є лише прогноз чи можливі інтервали; це не підтверджує порожній добовий графік. |
| `missing` | Недостатньо опублікованого покриття для дати чи груп. |
| `unpublished` | Оператор вимкнув публікацію. |
| `unsupported` | Адресу позначено як таку, що обслуговується непідтримуваним стороннім оператором. |
| `error` | Запит завершився помилкою або відповідь не вдалося перевірити. |

Бот додатково перевіряє інтервал і групи конкретного сповіщення, тому стан на сьогодні не гарантує покриття на завтра. Повідомлення про непідтверджений графік чи наближення відключення призупиняються, а перевірки автоматично продовжуються. Запис `Schedule has not been verified; notifications paused` у журналі може означати відсутність публікації, а не несправний токен Telegram. Не використовуйте календар **Останній відомий графік (лише перегляд)** як актуальне джерело сповіщень.

Підтверджена зміна групи може повідомлятися без графіка; це не означає «відключень немає».

Контроль живлення за свіжими локальними датчиками може працювати й без графіків ДТЕК. Режим `dtek_only` усе ще залежить від даних адреси ДТЕК і не вимірює фактичну наявність світла.

<a id="telegram"></a>
## Налаштування Telegram

Створіть бота через [@BotFather](https://t.me/BotFather), додайте його до потрібного чату та зберігайте токен приватно. Окремий бот для цього застосунку допоможе уникнути конфліктів між збирачами оновлень.

| Призначення | Налаштування |
| --- | --- |
| Особиста розмова | Відкрийте бота й натисніть **Розпочати**, щоб він міг вам писати. |
| Група/супергрупа | Додайте бота, дозвольте повідомлення. Для закріпленого статусу надайте право закріплення. |
| Канал | Додайте бота адміністратором із правами публікації та редагування своїх повідомлень. |

### Найпростіше: повідомлення лише собі

Створіть бота, введіть його токен у застосунку та запустіть його. Надішліть `/start`, потім оберіть себе зі знайдених одержувачів на кроці **Telegram**. Типовий `telegram_chat_id` можна залишити порожнім. За потреби введіть числовий ID вручну: особистий ID додатний, ID групи/каналу зазвичай від’ємний. Особистий `@username` не замінює числовий ID.

Налаштуйте адресу в HA та увімкніть потрібні повідомлення. `feedback_enabled` для звичайного надсилання не потрібен. Натискання Start дозволяє боту писати вам, але не реєструє адресу чи підписку автоматично: це бот сповіщень із налаштуванням у HA, а не майстер налаштування командами Telegram.

Якщо не потрібне закріплення, вимкніть `status_message.pin` або весь `status_message.enabled`. Значення `delivery_mode: pinned_edit` разом із `pin: false` продовжує редагувати одне звичайне повідомлення. У групі це також дає змогу працювати без права закріплення. [Права закріплення Telegram](https://core.telegram.org/bots/api#pinchatmessage).

Для кожної адреси задається одне призначення; автоматичної підписки довільних користувачів чи налаштування окремих тем форуму наразі немає. Якщо група перетворилася на супергрупу та її ID змінився, оновіть ID в параметрах і перезапустіть застосунок.

<a id="destinations"></a>
### Кілька адрес, чатів та ботів

Одне встановлення може стежити за кількома будинками через одного чи кількох Telegram-ботів. Наявні адреси використовують **Основного бота** з токеном і чатом із конфігурації застосунку HA. Для кожної адреси обирається один профіль бота; порожній чат адреси означає чат за замовчуванням цього профілю. Кожен обраний бот повинен мати право писати у свій чат.

Наприклад, ця конфігурація відстежує всі групи двох будинків. Перший використовує головний чат, другий — окрему групу. Замініть вигадані префікси через виявлення адрес, а приклад ID чату — на свій:

```yaml
addresses:
  - entity_prefix: vulytsia_prykladna_12a
    display_name: Приклад будинку А
    selected_group: ""
  - entity_prefix: dtek_krem_0123456789abcdef
    display_name: Приклад будинку Б
    selected_group: ""
    telegram_chat_id: "-1001234567890"
```

Щоб використати іншого бота:

1. Створіть його через @BotFather, додайте до групи/каналу або натисніть **Розпочати** в особистій розмові.
2. На вкладці **Telegram-боти** введіть назву, токен і чат за замовчуванням. Чат також можна задавати окремо для кожної адреси.
3. Натисніть **Перевірити токен і зберегти бота**. Застосунок викликає Telegram `getMe` та показує `@username`; ця перевірка не надсилає повідомлень і не перевіряє права в чаті.
4. На вкладці **Налаштування** оберіть бота для адреси. Натисніть **Застосувати**, щоб застосувати зміни профілю та адреси.
5. Для перевірки доставки задайте **Тестовий чат** у профілі та скористайтеся **Шаблони → Надіслати тест**. Кнопка використовує лише тестовий чат обраного бота. Якщо він відсутній чи недоступний, робоча група не використовується як запасний варіант.

Один профіль може обслуговувати кілька адрес. Повторне додавання того самого бота відхиляється, щоб не запускати збирачі оновлень, які конфліктують. Новий токен **того самого** бота можна зберегти в наявний профіль; для іншого бота створіть новий. Порожнє поле токена при редагуванні зберігає попередній токен. Профіль, що використовується збереженими або активними адресами, не можна видалити: спочатку змініть адреси, збережіть і перезапустіть застосунок.

Робочий YAML містить лише `telegram_bot_id` (`default` або ID з експортованої адреси), без токенів додаткових ботів. Імпорт зберігає це посилання: додайте відповідного бота на іншому HA або оберіть інший профіль перед збереженням. Якщо профілю немає, адреса призупиняється; автоматичного перемикання на основного бота немає.

Клієнти, журнали доставки та збирачі вхідних оновлень відокремлені для кожного бота. Помилка Telegram чи обмеження частоти одного бота не зупиняє обробники інших. ID статусу та підтвердження сповіщень прив’язані до бота, чату, тестового/робочого режиму та адреси. Зміна бота чи чату створює новий статус; старе повідомлення залишається в попередньому чаті, його можна видалити вручну. Заміна токена того самого бота зберігає статус. Перше оновлення автоматично переносить стан і журнал основного бота; перед оновленням зробіть приватну резервну копію.

**Один одержувач на профіль.** Щоб надсилати графіки того самого будинку в інший чат, скористайтеся **Клонувати** в редакторі: копія отримає окремий стабільний ID профілю, сповіщення та історію доставки. Префікс будинку може збігатися; ID профілів мають відрізнятися. Самостійні підписки користувачів і теми форумів не підтримуються. Для кількох профілів достатньо одного встановлення застосунку.

### Як знайти ID чату

Поруч із полями ID редактор пропонує список одержувачів. Увімкніть **Приймання команд**, напишіть боту `/start`, потім натисніть **Оновити** в редакторі. Групи й канали з’являються після нового повідомлення чи події зміни участі бота. Спершу оберіть потрібного бота; особистий профіль показує лише приватних користувачів. Ручне введення залишається доступним, саме виявлення не надає доступу. Докладніше — [виявлені одержувачі](docs/PERSONAL.uk.md#виявлені-одержувачі-telegram).

Якщо цей чат уже використовується в довіреній конфігурації HA, скопіюйте числовий ID звідти. Інакше отримайте його безпосередньо від Telegram через власного бота:

1. Зупиніть усі застосунки, які отримують оновлення цього бота. Зробіть це **до** ввімкнення збору зворотного зв’язку.
2. Надішліть нове повідомлення: `/start` в особистій розмові, `/start@YourBotUsername` у групі або звичайний допис адміністратора в каналі.
3. Збережіть код нижче як `telegram_chat_id.py` на комп’ютері з Python 3 і запустіть `python3 telegram_chat_id.py`. Він запитає токен без відображення введення та покаже ID й назви чатів. Повідомлень не надсилає, оновлень не підтверджує.
4. Скопіюйте ID потрібного чату разом зі знаком мінус до `telegram_chat_id`. Закрийте скрипт перед запуском застосунку.

```python
import getpass
import json
import urllib.error
import urllib.request

bot_token = getpass.getpass("Токен бота: ")
request = urllib.request.Request(
    "https://api.telegram.org/bot" + bot_token + "/getUpdates",
    data=b"timeout=0",
)
try:
    with urllib.request.urlopen(request, timeout=20) as response:
        payload = json.load(response)
except urllib.error.URLError:
    raise SystemExit("Помилка запиту. Перевірте токен, мережу й інші збирачі.") from None
seen = set()
for update in payload.get("result", []):
    message = update.get("message") or update.get("channel_post") or {}
    chat = message.get("chat", {})
    if "id" in chat and chat["id"] not in seen:
        seen.add(chat["id"])
        print(chat["id"], chat.get("title") or chat.get("username") or chat["type"])
if not seen:
    print("Чат не знайдено. Надішліть нове повідомлення та повторіть спробу.")
```

Налаштований webhook конфліктує з `getUpdates`; не видаляйте webhook іншого сервісу лише заради тесту. Використайте окремого бота. [API оновлень Telegram](https://core.telegram.org/bots/api#getupdates) і [правила приватності ботів](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get) пояснюють, які нові повідомлення він отримує. Бот не є універсальним засобом читання історії чатів.

**Профіль** поєднує один будинок/рахунок, одного одержувача та налаштування сповіщень. **Telegram-бот** — бот із токеном BotFather; його можуть використовувати кілька профілів. **Датчик живлення** показує вольти, герци або наявність мережі. **Датчик енергії** показує накопичувальні кВт·год і налаштовується в DTEK Monitor для підказок показів.

<a id="configuration"></a>
## Де зберігаються параметри

Налаштування розділені за призначенням:

| Місце | Параметри |
| --- | --- |
| Вкладка **Конфігурація** застосунку в HA | `telegram_bot_token`, `telegram_chat_id`, додаткові `test_chat_id`, `feedback_enabled` (типово `false`). Після зміни перезапустіть застосунок. |
| Вебредактор застосунку | Адреси, правила живлення/напруги, сповіщення та шаблони. Зміни адрес і робочих параметрів застосовуйте через **Застосувати**. |
| Вкладка **Telegram-боти** | Додаткові профілі ботів, основні/тестові чати та зворотний зв’язок. **Перевірити токен і зберегти бота** зберігає профіль; перезапуск застосовує його до сповіщень. |

Редактор записує робочі параметри до `dtek_telegram_bot.yaml` у каталозі конфігурації HA. Усередині цього застосунку шлях — `/homeassistant/dtek_telegram_bot.yaml`; у файловому редакторі HA той самий файл може бути видимим як `/config/dtek_telegram_bot.yaml`. `/data/config.yaml` — запасний шлях; наявна запасна конфігурація копіюється, коли основний шлях уперше стає доступним. Не підтримуйте різні конфігурації у двох файлах.

`ha_token` — необов’язковий резервний токен авторизації HA. За звичайного запуску через Supervisor залиште його порожнім. JSON-експорт редактора не містить резервного токена HA та токенів Telegram, але містить адреси й ID чатів. Сам робочий YAML може містити токен HA. Перевіряйте файли перед публікацією.

### Безпечне редагування

Фонове оновлення показує живі дані та не замінює поля, які ви редагуєте. **Перевірити** перевіряє поточну чернетку й показує знімок її результату, але не зберігає її. **Зберегти конфіг** записує налаштування; **Застосувати** також застосовує їх до запущеного застосунку. Якщо продовжити введення під час збереження, пізніші зміни залишаться незбереженими.

Чернетки конфігурації та окремих шаблонів переживають перезавантаження сторінки в тій самій вкладці, якщо доступне сесійне сховище браузера. Закриття вкладки може їх видалити; важливу чернетку конфігурації спочатку експортуйте. Перемикання шаблонів чи адрес не стирає їхні чернетки. Прев’ю використовує поточний текст без збереження.

Якщо інша вкладка або редагування файлу змінить збережену версію, застосунок повідомить про конфлікт замість перезапису. Експортуйте чернетку конфігурації (або скопіюйте текст шаблону), натисніть **Завантажити збережене** й узгодьте зміни. Ця дія відкидає поточну чернетку після підтвердження.

Токен бота залишається лише в поточній формі до надсилання; API не повертає його, а сховище чернеток браузера не записує. Фонове оновлення зберігає введення, але закриття/перезавантаження сторінки видаляє незбережені поля профілю. Одночасні зміни профілів також перевіряються: при конфлікті натисніть **Завантажити профіль знову** та узгодьте зміни.

### Поля адреси

| Поле | Значення |
| --- | --- |
| `entity_prefix` | Спільна частина ID сутностей адреси. Використовуйте автоматичне виявлення: це не обов’язково назва вулиці. |
| `display_name` | Зрозуміла назва в повідомленнях; порожня дозволяє визначити її через HA. |
| `telegram_bot_id` | Профіль бота: `default` використовує наявний токен Supervisor; додаткового бота оберіть у редакторі. |
| `telegram_chat_id` | Окремий чат адреси; порожній використовує чат обраного бота. Тестовий режим цього бота має пріоритет над обома. |
| `selected_group` | Порожнє поле відстежує всі групи адреси. Обирайте лише відому вам групу. |

Наприклад, для `sensor.dtek_krem_0123456789abcdef_outage_status` префікс — `dtek_krem_0123456789abcdef`. Якщо збережена обрана група зникає з адреси, обробка графіка очікує коректного вибору, а не вгадує заміну.

Для операторів із прихованими ID зазвичай залишайте `selected_group` порожнім і використовуйте відображувані варіанти. Звернення до регіональних сайтів і вибір оператора належать до [DTEK Monitor](https://github.com/groove-max/ha-dtek-monitor/blob/main/README.uk.md).

<a id="power"></a>
## Налаштування фактичного стану живлення

Спочатку скористайтеся [таблицею режимів](README.uk.md#power-detection). ID нижче — приклади: замініть їх через виявлення адрес і сторінки пристроїв HA.

### Нове налаштування: датчики Home Assistant

**Додати профіль** і **Налаштувати** використовують однакові чотири кроки: джерело даних, Telegram, сповіщення та перевірку. Натисніть **Застосувати** для перевірки, збереження й перезапуску. **Додаткові дії** містять імпорт/експорт і збереження без запуску; **Інструменти** — шаблони, пошук та діагностику. Загальні параметри приймання команд і резервного токена — під картками профілів.

На кроці **Telegram** оберіть наявного бота або **Додати іншого бота**. У вікні введіть назву й токен від BotFather. Збереження перевірить токен і вибере бота для профілю. **Запустити збережені налаштування** перезапускає застосунок із налаштуваннями на диску; незавершений профіль залишається чернеткою у браузері. Інші збережені зміни також набудуть чинності. Дочекайтеся підключення, напишіть боту `/start`, натисніть **Оновити одержувачів** і явно оберіть користувача чи чат. ID також можна ввести вручну. Токен основного бота й надалі задається в конфігурації застосунку HA.

Крок **Перевірка** показує рахунок/адресу, бота, ім’я та ID одержувача, сповіщення, датчики живлення й їхні ролі, контроль напруги та дозвіл передачі показів. **Застосувати** зберігає всі профілі й перезапускає застосунок. Незавершену форму токена спочатку збережіть або скасуйте. Попередні схеми живлення доступні в **Додатково: сумісність зі старими схемами**; наявні параметри збережено. Кнопка **Усі розділи** відкриває розгорнутий редактор за потреби.

Після **Застосувати** дочекайтеся повідомлення **Налаштування застосовано**: редактор перевіряє, що застосунок перезапустився зі збереженими налаштуваннями. Саме **Збережено** ще не означає, що вони працюють. Якщо перезапуск не вдався або не підтверджений протягом трьох хвилин, редактор залишає помилку видимою; налаштування залишаються збереженими. Повторіть **Застосувати** або перезапустіть **DTEK Telegram Bot** зі сторінки застосунку в HA. Перезапускати весь Home Assistant не потрібно. Сторінку редактора можна оновлювати під час очікування; нові незбережені зміни залишаться окремою чернеткою.

Переходи між кроками, фонові оновлення й перезавантаження сторінки зберігають чернетки профілів. Незбережений токен бота залишається лише в поточній формі, без запису у сховище браузера. Вибір виявленого користувача Telegram не надає доступу до застосування профілю.


Для нових датчиків використовуйте `power.mode: sources`: бінарний статус, напругу або частоту, з необов’язковим другим незалежним джерелом. Напруга для повідомлень налаштовується окремо. Повний посібник із прикладами та обмеженнями: [Датчики живлення](docs/POWER.uk.md).

Нижче збережено приклади сумісних схем. Оновлення не змінює їхні датчики, затримки, MQTT-топіки чи пофазову поведінку. Перехід на нову схему виконуйте явно в редакторі.

### Один датчик: `voltage_only`

Датчик має вимірювати **напругу на вході мережі у вольтах**, працювати під час відключення та передавати реальні значення, зокрема нуль. Його мережа/шлюз і HA також потребують резервного живлення. Налаштуйте періодичне передавання навіть незмінних значень. Датчик частоти не можна вказувати в `voltage.entities`.

Повний приклад робочого YAML для однієї адреси. `voltage.enabled: false` вимикає окремі сповіщення про якість напруги, а не використання вимірювань для визначення живлення:

```yaml
addresses:
  - entity_prefix: dtek_krem_0123456789abcdef
    display_name: Приклад будинку
    power:
      enabled: true
      mode: voltage_only
      loss_delay: 10
      restore_delay: 30
      telemetry_notifications: false
    voltage:
      enabled: false
      entities:
        - entity: sensor.inverter_ac_input_voltage
          label: L1
      present_above: 50
      max_age_seconds: 150
```

`loss_entity` і `loss_mqtt_topic` залишаються порожніми. `confirm_timeout` у цьому режимі не застосовується. Якщо єдиний датчик вимикається разом із мережею, він придатний для вимірювання наявності напруги, але його зникнення не підтверджує відключення.

### Два датчики: `loss_plus_voltage`

Використайте резервований датчик втрати мережі **на тій самій лінії** разом із лічильником напруги, наприклад ATORCH. Незалежне джерело має явно повідомляти про відсутність мережі: наприклад, частота на AC-вході інвертора нижча за 1 Гц. Недоступність цього датчика не є сигналом втрати мережі.

Замініть секції `power` і `voltage` всередині адреси цим прикладом:

```yaml
power:
  enabled: true
  mode: loss_plus_voltage
  loss_entity: sensor.inverter_ac_grid_frequency
  loss_state: "<1"
  loss_delay: 10
  confirm_timeout: 15
  restore_delay: 30
  telemetry_notifications: false
voltage:
  enabled: false
  entities:
    - entity: sensor.atorch_voltage
      label: L1
  present_above: 50
  max_age_seconds: 150
```

| Показання | Результат |
| --- | --- |
| Свіжа низька/нульова напруга + свіжий сигнал втрати мережі від інвертора | Підтверджене відключення після затримки втрати. |
| Низька/нульова напруга, інвертор показує наявність мережі або не має достовірного показання | Невідомий локальний стан; повернення напруги не створює пару повідомлень про відключення/відновлення. |
| Свіжий сигнал втрати мережі від інвертора + недоступний ATORCH або старе завмерле значення | Підтверджене відключення після затримок підтвердження й втрати. Порядок подій неважливий. |
| Сигнал втрати мережі + нова додатна напруга після нього | Суперечність: сигнал не перекриває свіжої напруги. |
| ATORCH недоступний, інвертор показує наявність мережі | Невідомий локальний стан, без хибного відключення. |
| Обидва джерела застарілі/недоступні | Невідомо, а не підтверджена втрата живлення. |
| Інвертор показує повернення мережі, ATORCH ще недоступний | Очікування свіжої напруги перед повідомленням про відновлення. |
| Свіжа напруга повернулася та залишається достовірною протягом затримки | Повідомлення про відновлення, якщо раніше відключення було підтверджене. |

Повторні повідомлення про недоступність не перезапускають таймери та не перетворюють підтверджене відключення на тимчасову втрату даних, доки незалежний сигнал відсутності мережі залишається свіжим.

### Затримки та актуальність

Значення у прикладах — початкові орієнтири для джерела, яке звітує приблизно раз на хвилину, **а не універсальні рекомендації для пристроїв чи типові значення**.

| Параметр | Типово | Призначення |
| --- | --- | --- |
| `power.loss_delay` | 30 с | Стійка відсутність перед повідомленням про втрату живлення. |
| `power.confirm_timeout` | 15 с | Час підтвердження у режимі двох сигналів перед відхиленням старої напруги. |
| `power.restore_delay` | 10 с | Стійка достовірна наявність перед відновленням. |
| `voltage.max_age_seconds` | 600 с | Максимальний вік показання; доберіть за реальним інтервалом звітування. |
| `voltage.present_above` | 50 В | Напруга від цього програмного порога вважається наявною. |
| `power.telemetry_notifications` | `false` | Окремі сповіщення про втрату/повернення даних. Статус оновлюється й без них. |
| `power.telemetry_loss_delay` | 20 с | Затримка необов’язкового сповіщення про втрату даних. |

Свіжа низька/нульова напруга сама по собі може підтвердити відсутність у `voltage_only`. У `loss_plus_voltage` для повного відключення також потрібен свіжий незалежний сигнал втрати мережі; затримка втрати починається лише тоді, коли обидва джерела підтверджують відсутність. Відсутні, некоректні, від’ємні, нескінченні, відновлені зі сховища чи застарілі значення самі по собі цього не підтверджують. Перевірка кожні 5 секунд виявляє мовчазне старіння даних. Незмінне, але щойно передане значення придатне; повторні показання не перезапускають затримку. Невідомі або суперечливі дані переривають очікуваний перехід.

У прикладі з двома датчиками враховуйте близько 15 + 10 секунд після отримання незалежного сигналу втрати та час обробки/перевірки. Щоб оцінити затримку від фізичного відключення, додайте інтервал звітування пристрою. Максимальний вік даних — не затримка підтвердження відключення.

`last_reported` HA (або запасний `last_updated`) фіксує звітування в HA, а не гарантовано нове вимірювання на пристрої. Хмарна інтеграція може повторно публікувати старі дані. Старий параметр `unavailable_as_missing` збережений для сумісності, але більше не перетворює відсутність даних на відключення.

### Незалежне джерело MQTT

Для MQTT-датчика втрати мережі можна вказати точний топік стану в `power.loss_mqtt_topic`. Застосунок пасивно підписується через HA, ігнорує повторне retained-повідомлення та вимагає свіжого повідомлення, яке збігається зі станом сутності. Маски топіків не приймаються. З’єднання HA має дозволяти `mqtt/subscribe` — потрібен адміністраторський доступ. Облікові дані MQTT-брокера цьому застосунку не потрібні.

Використовуйте активний топік пристрою, а не старий із залишеним retained-значенням. Якщо MQTT-сенсору HA потрібен числовий шаблон, `{{ value | float(none) }}` обробляє числовий текст/байти, не перетворюючи помилковий вміст на нуль. Це налаштування MQTT-сенсора HA, а не шаблону Telegram. Дивіться [поведінку MQTT-сенсорів HA](https://www.home-assistant.io/integrations/sensor.mqtt/).

### Кілька фаз

Використовуйте сумісну схему `voltage_only` або `loss_plus_voltage`. `sources` узгоджує датчики однієї лінії, а не окремі фази.

Додайте сутності напруги з підписами `L1`, `L2`, `L3`. `on` означає наявність усіх налаштованих фаз; `off` потребує доказів відсутності всіх. `partial` — частина живлення є, а інші фази відсутні або невідомі; статус розрізняє ці випадки. Невизначеність не створює сповіщення про втрату фази. Незалежний сигнал має описувати саме контрольовану лінію/схему живлення.

Раніше підтверджене відключення зберігається в історії після втрати даних, тому достовірне повернення напруги все ще може спричинити повідомлення про відновлення. Якщо прогалини заважають обчисленню тривалості, вона позначається як невідома.

<a id="notifications"></a>
## Які сповіщення ввімкнути

Кожна функція має `enabled`. `silent` вимикає звук сповіщення Telegram, **а не саме повідомлення**.

| Секція | Призначення / основні параметри |
| --- | --- |
| `schedule_change` | Зміни опублікованого графіка; порожній графік оголошується лише за достатнього покриття публікації. |
| `group_change` | Зміна груп адреси та їхній графік; без дубля повідомлення про той самий графік. |
| `emergency` | Початок/завершення, причина та орієнтовний час відновлення за даними оператора. |
| `upcoming_outage` | `minutes` до початку (типово 10); `power_filter`: `always`, `only_when_available` (типово), `only_when_missing`. |
| `power` | Втрата/відновлення за обраним режимом; додаткові `phase_notifications`. |
| `voltage` | Окремі сповіщення про напругу: типово `low: 195`, `high: 245`, `hysteresis: 5`, `delay: 15`. |
| `status_message` | `pinned_edit` (типово) або `send_new`; `pin`, `silent`, `update_interval` (300 с), `min_update_interval` (10 с). |

Для повернення напруги в норму застосовується гістерезис: після виходу за межу значення має повернутися всередину нормального діапазону на заданий запас. Для спільного чату почніть із закріпленого статусу й потрібних мешканцям подій. У режимі `dtek_only` одночасно ввімкнені повідомлення про відключення ДТЕК та живлення можуть двічі описати ту саму подію оператора — оберіть потрібні категорії.

Графік і локальні вимірювання залишаються окремими джерелами. Під час збою ДТЕК контроль фактичного живлення може продовжуватися; збережені графіки не запускають автоматичних повідомлень про графік, групи чи наближення відключення.

Відключення, що триває через опівніч, вважається однією подією. Поділ або
об’єднання його записів у календарі, переклад назви чи інший запис часового поясу
не спричиняють повторного повідомлення про зміну графіка. Порівняння розрізняє
групи й охоплює ті самі два дні, що показані в повідомленні з графіком.

Попередження надсилається один раз для групи й часу початку. Уточнений час
завершення не запускає повторного попередження: він відображається в закріпленому
статусі та повідомленні про зміну графіка, якщо цю функцію ввімкнено. Інший початок
або інша група залишаються окремими подіями. Оновлення та перезапуск застосунку
зберігають підтвердження попередніх надсилань, зокрема невизначені результати Telegram.

Якщо інтеграція передає межі перевіреної публікації, бот шукає події лише в
безперервно перевіреному проміжку для обраної групи чи груп. Коли подія
закінчується на цій межі, попередження й закріплений статус показують, що її
завершення невідоме. Наприклад, графік лише до опівночі не обіцяє повернення світла
о 00:00. Це час за графіком, а не вимірювання фактичного живлення. Старі інтеграції
без відомостей про межі публікації зберігають попередню поведінку. Нові часові
сенсори та окремий календар ремонтів не вмикають додаткових сповіщень автоматично;
бот продовжує використовувати календар відключень будинку.

<a id="templates"></a>
## Як змінити текст повідомлень

Публічне привітання — це шаблон **Привітання · welcome**. Його текст і посилання можна повністю замінити. Він спільний для всіх ботів цього add-on та отримує лише `telegram_user_id`, без даних рахунків. Перемикач розташований у **Загальні та службові налаштування → Привітання для нових користувачів**; стандартне привітання з GitHub типово ввімкнене.

Відкрийте **Шаблони**, оберіть шаблон, перегляньте результат, відредагуйте й збережіть перевизначення. Скидання видаляє власний варіант і повертає стандартний. Тест надсилає справжнє повідомлення лише в тестовий чат обраного бота. Спочатку задайте його; робочий чат не використовується як запасний варіант.

Використовується Jinja. Доступні поля показані в редакторі й залежать від повідомлення. `group`, `groups`, `selected_group`, `old_group`, `new_group` уже враховують приховані підписи; `groups_public` показує, чи існують публічні номери груп.

У `upcoming_outage` поле `end_confirmed` вказує, чи підтверджує опублікований графік
час завершення інтервалу. Якщо ні, `end` містить `невідомо` замість часу: старий
власний шаблон не отримає оманливе значення опівночі. Стандартний шаблон показує
окремий рядок про невідоме завершення. У власному шаблоні використовуйте
`{% if end_confirmed %}` для свого формулювання. Попередній перегляд використовує
ті самі правила, що й робочі попередження.

Розміщуйте заголовок, інтервал і пояснення на окремих рядках. Обрізання пробілів Jinja прибирає перенос після блочного тегу, наприклад `{% endif %}`: перевіряйте **готовий текст** для всіх гілок шаблону. Явний `{{ '\n' }}` дозволяє зберегти потрібний перенос.

Перевизначення зберігаються в `/data/templates/*.j2` і переживають оновлення. Тому нова версія застосунку не виправить старий власний шаблон автоматично. `export_default_templates: true` копіює стандартні файли лише за їх відсутності; залиште вимкненим, якщо вони вам не потрібні.

<a id="testing"></a>
## Тестування без повідомлень в основний чат

Особистий профіль та його тести шаблонів можуть надсилати дані лише в дозволений приватний чат; загальна тестова група для них відхиляється. [Особистий режим](docs/PERSONAL.uk.md).

1. Виберіть тестовий чат: натисніть **Розпочати** в особистій розмові або додайте бота до тестової групи/каналу з потрібними правами.
2. Для **Основного бота** задайте параметр Supervisor `test_chat_id` і перезапустіть застосунок. Він спрямовує всі повідомлення цього бота в тестовий чат, як і раніше.
3. Для додаткового бота задайте **Тестовий чат** у профілі. Кнопка **Надіслати тест** використовує його одразу після збереження профілю. Для перенаправлення всіх сповіщень також увімкніть **Тестовий режим**, збережіть і перезапустіть. Інші боти продовжують використовувати власні чати.
4. У тестовому режимі надсилання, редагування та закріплення використовують тестовий чат; змінюються лише повідомлення, відомі його журналу. Для режиму обов’язково потрібен тестовий чат.
5. Необов’язкове **Збирання зворотного зв’язку** (`feedback_enabled`) зберігає нові доступні боту дописи тестового чату. Потрібні тестовий режим, один збирач на токен і відсутність webhook. Помилка запуску показується на вкладці **Telegram-боти**, не зупиняючи інших ботів.
6. Зупиніть інші екземпляри з тим самим токеном. Журнали ізольовані в `/data/bots/<bot-id>/<mode>/telegram.sqlite`, а стан адрес зберігається за окремими маршрутами в `/data/state.json`.

Вхідний зворотний зв’язок залежить від прав і приватності Telegram. У каналі без прив’язаної групи обговорень використовуйте дописи адміністратора, а не очікуйте відповідей користувачів. Збирач не імпортує довільну стару історію чату.

Локальний SQLite-журнал містить вихідні тексти, результати API та контекст адрес/груп; зворотний зв’язок додає вхідні повідомлення. Зберігається до 10 000 записів подій. Це приватні дані. Супроводжувач може читати `telegram.sqlite` через SSH у режимі SQLite лише для читання. Журнал підтверджує результат доставки, а не прочитання людьми.

Явні тимчасові помилки можуть спричинити обмежені повтори після перевірки актуальності. Неоднозначні мережеві результати записуються як невизначені, без сліпого повторного надсилання. Гарантії доставки «рівно один раз» тут немає.

<a id="updates"></a>
## Резервні копії, оновлення та перенесення

[Оновлення й відкат](docs/UPGRADING.uk.md). Для особистого режиму спочатку оновіть інтеграцію.

- Зберігайте резервні копії даних застосунку та конфігурації HA, включно з `dtek_telegram_bot.yaml` і власними шаблонами.
- Прочитайте [історію змін](CHANGELOG.md), оновіть застосунок і перевірте активні параметри та чат.
- Для перенесення використайте експорт/імпорт адрес або чернетки конфігурації. Це не створює сутностей HA та не переносить облікові дані ботів. Окремо задайте основний токен/чат, створіть додаткові профілі, перевірте вибір бота для кожної адреси й узгодьте ID сутностей.
- Перед виходом із тестового режиму зупиніть тестовий екземпляр, очистьте `test_chat_id` основного бота або вимкніть **Тестовий режим** додаткового профілю, перевірте його робочий чат і перезапустіть. Робочий режим відновлює власний збережений стан; не копіюйте тестові ID повідомлень або чергу сповіщень у нього.

Основний токен Telegram зберігається в параметрах Supervisor. Додаткові токени зберігаються без шифрування у приватному файлі застосунку `/data/telegram_bots.json` із правами лише для власника (0600); їх немає в JSON-експорті редактора й діагностиці. Резервні копії застосунку містять цей файл. Резервний токен HA також може бути в робочому YAML. Включайте їх лише до приватних копій. Якщо токен став публічним, замініть його через сервіс, який його видав.

Якщо проблему не розв’язано, скористайтеся [таблицею діагностики](README.uk.md#troubleshooting), потім створіть issue з версіями, режимом, інтервалом звітування та потрібними журналами без приватних даних. Для розробників є [посібник учасника](CONTRIBUTING.uk.md).
